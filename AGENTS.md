# Rules for any AI session on crystalproteins-poc

## Git

- Work on `develop`, never `main`. The owner merges and pushes `main`.
- Git identity per command, never written to config:
  `git -c user.name="Pedro Morales" -c user.email="pedro@triview.com" commit …`
- Commit message: one plain sentence saying what was wrong or missing and what is true now, then the trailer lines.
- Commit every report, journal entry and field note in the session that writes it.
- Over the desktop-app bridge, ask for delete permission on the repo folder before any git work (git removes its own lock files).

## Working

- Tests for all new code; run them until green before handing over. Say the counts.
- Verify vendor, format and library claims (DICOM tags, TotalSegmentator classes and licence, etcher specs, Sketchfab, three.js APIs) by web search and cite them in the report. Do not guess or approximate.
- Singular names for every schema object, so `table.column` reads naturally (`layer.name`, `structure.label`).
- Customer data is confidential: never commit it, never paste it into a blog or a public page. Real files live in `samples/` or `field/inbox/` (both gitignored); tests use synthetic data (`make_phantom.py`) or tiny generated meshes.
- The mesh is the primary product. Engraving dots are generated by the owner's own tooling; the dot preview is only a sanity check.
- The viewer must stay self-contained: no runtime CDN imports (a public viewer hung on them once). Libraries are bundled by `build_viewer.py`.
- Ask when intent is unclear (customer flow, file taxonomy, sharing rules, UI). Don't guess.

## Screenshots and notes for the blog

At every milestone (success, failure, roadblock) take or ask for a screenshot, save it under `field/YYYY-MM-DD/screenshots/NN-what-it-shows.png` with a README line each (what it shows, which milestone). A blog draft names the screenshots it wants. Screenshots must not show customer data.

## Every review or research session (a Claude app chat) that decides work ends with an iteration prompt

The next `docs/prompts/iteration-N.md` in the shape of `iteration-1.md`; point HANDOFF at it; give the owner the block to paste; commit it.

## Lines of work

- **iteration** (code: ingester, pipeline, viewer). Runs locally on the Mac in Claude Code. Prompts `docs/prompts/iteration-N.md`, reports `docs/reports/NN-title.md`. Tests: `npm run test:fast` while working, `npm run build && npm test` before handing over. Each iteration writes the next prompt itself.

Add a section here for each new line (where it runs, its prompt file name, its report numbering, its own test command, and that each iteration writes the next prompt).

## Reviewer agents — one brief, two copies, always in sync

None yet. Each one lives in `.claude/agents/<name>.md` (Claude Code loads it by name) and its body is mirrored verbatim in `docs/KICKOFF-PROMPT.md` between `<!-- agent-body: <name> -->` and `<!-- /agent-body -->` (a Claude app chat can't load `.claude/`). Change both in the same commit: edit the agent file, `node scripts/agent-sync.mjs --write`, then `node scripts/agent-sync.mjs` must report them in sync.

## Every iteration ends with

1. A report `docs/reports/NN-title.md`: what was asked, found, built, tested (counts), what is owed to the owner, the checklist for the next real-world use.
2. A JOURNAL entry.
3. HANDOFF's Current state and Open items updated.
4. A commit on `develop`.
5. Whenever there is something worth telling or a step that shows progression, a blog draft (`draft: true`, first person, no personal or customer data — the owner publishes).
6. The next prompt `docs/prompts/iteration-(N+1).md`.
